# Lessons Learned

This file consolidates lessons that should shape the PR #70 recovery and future work. It intentionally corrects older repo guidance where the deployment target has changed.

## Current Recovery Corrections

1. Vercel is the active deployment target.
   - Older DigitalOcean docs are historical for this recovery.
   - Do not let `.do/*` or old handoff docs override `PR70_RECOVERY_PLAN.md`.

2. Path drift is one of the repo's main failure modes.
   - Current Vercel-oriented code uses `api/_lib/*`.
   - Older PRs may use `api/lib/*` or `story-generator/src/api/lib/*`.
   - Ported code must be normalized instead of creating another active copy.

3. Audio can contain story-generation value even when audio is deferred.
   - Mine emotion, speaker-tag, narrator-atmosphere, dialogue segmentation, and character-consistency ideas before closing audio PRs.
   - Do not restore active audio routes/services/tests unless explicitly requested.

4. PR #70 is a direction-setting baseline, not a license to discard working story generation.
   - Preserve current model, token, prompt, continuation, and streaming improvements unless #70 intentionally replaces them with something better.

## Lessons From Existing Repo Docs

1. Contracts define everything.
   - Update frontend and backend seams before implementation.
   - Test contract shape at boundaries, not only internal helper behavior.

2. Deduplication prevents drift.
   - Centralize Grok model names, token calculation, randomization helpers, author-style configuration, and story state models.
   - Duplicated story services caused repeated confusion and stale fixes.

3. Mock-first development helps, but mocks must not become product truth.
   - Keep mock paths useful for development.
   - Keep production story generation flowing through the real service seam.

4. Test infrastructure is part of feature work.
   - A migration is not healthy if tests are left for the end.
   - Fix or document test failures at the cluster where they are introduced.

5. AI model changes require full story-flow validation.
   - Check generation, continuation, streaming, and token budgeting together.
   - Model constants must not be hardcoded in several places.

6. Incremental refactoring works better than broad mixed rewrites.
   - After PR #70 lands as the deliberate baseline shift, every other capability should be a small, source-attributed port.

7. Documentation needs lifecycle control.
   - The repo has a history of many overlapping status docs.
   - Prefer one running changelog, one lessons file, one PR ledger, and one final report for this recovery.

8. Deployment configuration is product code.
   - Vercel config, build commands, API route layout, and helper-file placement can break the app as surely as TypeScript code can.

## New Lessons During This Recovery

### 2026-08-24

- Run a hosted analyzer's own rules locally when its findings are unreachable. SonarCloud failed PR #206 on `B Maintainability Rating on New Code` while its API answered only through an egress proxy that denies `CONNECT sonarcloud.io:443`, and it left no inline comment. Guessing at plausible smells cost a commit and did not clear the gate. SonarCloud's JS/TS rules are SonarJS, which ships as `eslint-plugin-sonarjs`: installed outside the repository and pointed at copies of the changed files, it named the finding in one run. Install it outside the tree — `node_modules` is tracked here, so installing into the repo dirties the slice diff.
- Lint the pre-change files from `origin/main` as well, to separate findings that are new to the slice from ones the gate has already accepted. In #206 that comparison showed the flagged block-splitter regex was pre-existing on `main` and counted only because moving it to a new file made it new code — without the comparison the obvious reading is that the new code introduced it.
- A moved file is new code to a quality gate. Extracting a shared helper re-submits every line it carries to the new-code rating, so a clean extraction can fail a gate that the original passed.
- Prove a regex rewrite is behaviour-preserving before trusting it, and measure the claim that motivated it. For #206 the old and new patterns were compared on seventeen representative inputs, including the near-miss cases that must not match, and timed on adversarial input: 2052 ms against 0.32 ms over 40,000 characters. That evidence is what separates a real super-linear fix from lint appeasement.

- Deleting a tag is not the same as removing it. `content.replace(/<[^>]*>/g, '')` closes the gap the tag held open, so `door.</p><p>Blood` becomes the single token `door.Blood`: word counts lose one word per boundary, sentence splits that need whitespace after `[.!?]` stop finding any, and paragraph-shaped measures see one paragraph. Four separate slices have now hit this in four different files (cliffhanger scan, quality heuristics, story service, image service). `api/_lib/utils/storyTextBlocks.ts` is the shared answer — `splitStoryIntoTextBlocks` for anything that reasons about paragraphs, `stripStoryHtmlToText` for anything that wants the reader's plain text. Reach for it instead of writing another local strip, and when a slice fixes one site, sweep for the rest in the same pass: `rg -n -F '<[^>]*>' -g '*.ts' api shared story-generator/src` finds every remaining in-place strip in one command, and as of this entry it returns nothing. Three of the four sites were found one slice at a time because nobody ran it.
- A malformed request is the caller's fault and must be answered as one. A route that reads `req.body.field` without checking the body throws into its own catch block, and that catch reports 500 `INTERNAL_ERROR` — telling the client the service failed and a retry might help, when only the caller can fix it. The runtime hands `req.body` over as `undefined`, a string, or an array whenever it could not parse a JSON object, so the guard has to cover all four shapes.
- An `EventSource` retries; a terminal error must therefore close it. A client that treats the server's `type: 'error'` chunk as ordinary progress leaves the stream open, and the browser reads the server's `res.end()` as a dropped connection and reconnects — restarting whatever expensive work the stream was carrying, on every retry, while the subscriber waits on an observable that never settles. Close the stream and settle the subscription at the terminal chunk, and unsubscribe rather than only dropping the handle: the teardown that closes the connection runs on unsubscribe, nowhere else.
- A job marked `running` needs a terminal state on every exit path, including the throw. Route code that awaits its work outside a `try` hands the throw to the framework's 500 handler and leaves the job row saying `running` — forever, on a durable store, with clients polling or streaming its events. Handled failure envelopes are the easy path to get right; the throw is the one that gets missed. Record it as a failure of the job, and put the thrown detail in the log rather than in the payload the caller reads.
- One env var, one parser. `ALLOWED_ORIGINS` is a comma-separated list, and any code that echoes it into a single-valued header instead of matching the request against it produces a header no browser accepts — a config that looks reasonable in the dashboard silently blocks every cross-origin call. When a second runtime (here the Node server beside the serverless routes) reads the same variable, give it the same parser rather than its own reading of the format.
- Escape sequences in a protocol terminator deserve their own test. `` `data: ${json}\\n\\n` `` in a template literal writes a backslash and an `n`, not a line ending, so every SSE frame the route produced was undeliverable while the code read as correct at a glance. Build the frame in one named function and assert against a parser that splits on the blank line the way a client does — a test that compares strings would have been written with the same typo.
- A heuristic that can only say yes is not a signal. Both identity-shaped quality dimensions scored every story the same way for the same reason: `\b[A-Z][a-z]+\b` matches the first word of every sentence, so a story with no cast reported four named characters, and `extractConcreteAnchors` filtered out the short tokens *before* pairing them, so the determiners its own weak-first-token list exists to reject were gone before the guard ran and "a door" was scored as a concrete anchor. Both bonuses cap at two or three hits, so both were collected in full by any story of a few sentences. When a scan has a rejection list, write the counterfactual test first — prose that should score zero — because a dimension that awards the same points to everything reads as working right up until someone checks what it refuses.
- Dropping tokens changes which words are adjacent. Filtering a token list and then reading pairs out of it welds two words that were never next to each other in the prose: "opened a door" becomes the phrase `opened door`. Filter after forming the pair, or the filter silently invents the evidence the pair is supposed to prove.
- A repeated query parameter is an ordinary URL, and a route that reads one as a string is broken in two different directions. `?themes=a&themes=b` arrives as an array: `themes.split(',')` throws, while `?creature=x&creature=y` does not throw at all — an array is truthy, so it passes validation and fails deep inside the service after the response has already committed to 200. Neither reaches the validator that exists to answer both. Read every possibly-repeated field through one helper that takes the first value, the way `corsPolicy`, `security`, and the blueprint parser already do.
- An SSE catch block has two callers, and only one of them can read a frame. Once `writeHead` has run, a `type: 'error'` frame is the only way to reach the client; before it, writing that frame sends a default 200 with no `text/event-stream` content type — a body neither an `EventSource` nor a JSON client can read, so a failure arrives as a success. Branch the catch on `res.headersSent`: JSON error above the stream, framed error inside it. A test double that does not model `headersSent` will hide this, so give the double the property Node's `ServerResponse` actually has.
- Decide the boundary before combining the tokens. A pattern that matches an optional compound — `[A-Z][a-z]+(?:\s+[A-Z][a-z]+)?` — hands the boundary test a pair, so rejecting "Then Mira" for starting the sentence discards "Mira" too, and a global matcher resumes past the whole match rather than offering the second word on its own. Match the full run and drop only the word that is actually on the boundary. The same shape appears anywhere a filter runs over groups instead of over members.
- A fix that removes one filter has to say what now rejects what the filter used to. Dropping the "tokens longer than two characters" rule from the anchor scan was right — it broke adjacency and made three deny-list entries unreachable — but the short words still needed rejecting, just as first halves of a pair rather than as tokens. Stating the replacement rule as a property (no one- or two-letter English word is a modifier that makes a noun specific) covers `in court` and `by car` as well as the `a`, `an`, `my` the old list named one at a time.
- Every guard added to a route handler spends complexity budget the linter is counting. One `if (!res.headersSent)` took `handler` from under SonarCloud's cognitive-complexity limit to over it. Extracting the block the guard belongs to — here the whole GET query read — costs nothing and leaves the handler with the shape its name claims; check the changed file with `eslint-plugin-sonarjs` before pushing rather than learning it from the quality gate.
- A punctuation mark belongs in a "sentence boundary" set only if the language actually capitalizes after it. Semicolons and dashes do not end sentences, so a capital following one is explained by nothing except the word being a proper noun — exactly the signal the scan is looking for. Including them inverted the test: "The lock broke; Mira pressed the blood oath" scored no character signals while the comma form scored two. Enumerate the marks from the capitalization rule, not from a general sense of "this separates clauses", and keep the genuinely ambiguous one (the ellipsis) on whichever side the dimension's error bias prefers.
- `writeHead`'s header argument silently wins over every `setHeader` before it. A route that carefully sets `Cache-Control: no-cache, no-transform` and then passes `'Cache-Control': 'no-cache'` to `writeHead` sends the second one; both lines read as correct and the file looks like it is setting the header twice for safety. The directive that got dropped was the one forbidding an intermediary from re-chunking the stream — the whole failure mode `X-Accel-Buffering: no` two lines above exists to prevent. Pass `writeHead` the status alone once the headers are set, and assert on the headers a client would actually receive rather than on the `setHeader` calls, because only the merged view shows which one survived.
- A hard-coded `method` in a catch block is a lie the moment a second method is supported. The streaming route accepted GET specifically so an `EventSource` could reach it, and then logged every failure as `POST` — while the `logInfo` at the top of the same handler recorded `req.method` correctly, so one request produced two log lines that disagreed. Request-derived context belongs in the log entry as the request's own value, never as a literal; a literal that was true when it was written stops being true without anything changing near it.
- `typeof x === 'number'` is a type check, not a range check, and a model's answer needs both. The evaluation route promised 0-100, rendered the field as `{{ score }}/100`, and passed the model's number through untouched — so an answer on the 1-10 scale these criteria are just as often written against reached the reader as `8/100` in the red band. The deterministic report in the same payload was clamping its own dimensions all along, so the two halves of one response disagreed about the scale. Clamp any externally-supplied number at the boundary to the range the consumer is written against, and put the clamp beside the default the missing-field case already uses.
- A keyword scan matches whole words or it matches the wrong ones. `content.includes('lie')` fires on `courtier`, `earlier`, `relief`, and `believed`; `'heart'` on `hearth`; `'want'` on `unwanted`; `'price'` on `priceless`; `'secret'` on `secretary`. Four separate slices have now hit this in four places (`extractThemesFromContent`, `extractSpicyLevelFromContent`, `analyzeEmotionalTone`'s `dominan` stem, and `storyLabEngine`'s `containsAny`), and every one of them fed a prompt or a stored answer rather than a log line, so the damage was a model being told the wrong thing about the reader's own story. `containsWholeWord` in `storyContentAnalysis.ts` is the shared reading. Two things make the repair honest rather than a coverage cut: spell out the inflections the substring form picked up for free (`dangerous` for `danger`, `threatening` for `threat`, `betrayal` for `betray`) so the scan keeps the matches it got right, and assert both directions — a whole-word matcher with no inflection table passes the "no false positives" half and quietly costs the scan its real signal. `rg -n "includes\('[a-z]{3,12}'\)" -g '*.ts' api shared story-generator/src` finds the remaining raw substring scans in one command; run it when a slice fixes one site rather than waiting for the next slice to find the next one.
- A cap and an ordering are one decision, and splitting them across layers loses rows silently. The cloud library ordered by the reader's `librarySort` at the route and capped at `limit 50` in the SQL, so `updated_at desc` chose which fifty survived and the reader's sort only rearranged the survivors: a `title_asc` library was the alphabetical order of the fifty most recently touched projects, missing whichever project should have been at the very top of it. The sibling in-memory adapter had no cap at all, so the two stores did not agree on what the library contained, and the response carried no total — a page that reports only its own length reads exactly like a complete one. Put the cap wherever the ordering that picks the items lives, apply it in one place for every adapter, and return the untruncated count so the truncation is visible.
- A validator that is careful about closed fields and silent about open ones is the shape to look for when hunting unbounded free text. `normalizeStoryLabProfilePreferences` checked five enum-shaped fields against their allowed sets and read three free-text ones through `typeof value === 'string'` — and the profile is *durable*, so the miss cost more than the blueprint routes' did: what a caller sent was stored and handed back on every read afterwards. One of the three, `noGoContent`, is the same field the blueprint parser caps at 320 characters, so the standing default for it was unbounded while the per-story value was not. Refuse rather than truncate when the field states a constraint the reader will rely on, cap it at the boundary the caller can see (`PUT`, not the normalizer every read also runs), and read the number from wherever the sibling route already enforces it.
- A sweep command only finds the spelling it was written for. The previous slice recorded `rg -n "includes\('[a-z]{3,12}'\)"` as the way to find remaining substring scans, and it returned clean while `CliffhangerService` still held six lists of them — because its needles live in a table and the call is `patterns.filter(pattern => text.includes(pattern))`, with a variable where the regex expected a literal. When a lesson names a grep, name the *variable* form beside the literal one (`\.includes\((needle|pattern|keyword|term|token)\b`), and treat a clean sweep as evidence about the pattern searched for rather than about the defect.
- Run the counterfactual before writing the prose that explains the bug. The first draft of the cliffhanger fix led on "`hidden` is inside `forbidden`" — a compelling claim in an app whose third theme seed is `forbidden_love`, and false: `forbidden` contains `bidden`. Nothing in the code review would have caught it; the fixture scoring 0 instead of the predicted `mystery` hit did. Every collision an explanation names should be one a test actually drives, because a plausible substring is exactly the kind of thing a reader will accept without checking.
- Adding a required field to a shared contract type is a breaking change to every literal that constructs it, and `tsc -p tsconfig.json` will not tell you. The Angular app and its specs are separate TypeScript projects: `totalProjectCount` typechecked clean against `tsconfig.json` and broke five `*.spec.ts` fixtures that build a `CloudStoryProjectList` by hand, which CI found and the local run did not. Two habits close it — run `scripts/recovery/preflight.sh --skip-status`, which is what CI runs and covers both projects plus the API tree, rather than one tsconfig; and when grepping for a type's consumers before changing it, do not filter `.spec.ts` out, because a test fixture is a consumer that only the spec project compiles.
